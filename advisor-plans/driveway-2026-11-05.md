## 1. Release blocker: underside sampling can miss a real collision

**Problem.** The editable-profile calculator can report positive clearance at a pose whose underside intersects a narrow ground peak. This undermines the promise to find the smallest gap. The 0.05-inch formula claim is supported for its specific examples, but is not an error bound for arbitrary profiles.

**Evidence.** Remote `static/js/driveway-geometry.js:158` chooses roughly one-inch underside samples; intervening ground vertices are not checked. Reproduced with the deployed `DrivewayGeometry` API:

```js
const G = DrivewayGeometry;
const car = { wheelbase:100, tireDiameter:1, frontOverhang:0,
  rearOverhang:0, frontHeight:0.05, rearHeight:0.05, clearance:0.05 };
const points = [{x:-100,y:0},{x:0.4,y:0},{x:0.5,y:0.1},
  {x:0.6,y:0},{x:200,y:0}];
const ground = G.buildGround(points);
const p = G.pose(ground, car, 'nose-in', -49);
console.log(G.validateCar(car), p.min, p.toWorld(49.5,0.05),
  G.heightAt(ground,0.5));
```

Output: validation `[]`; sampled minimum `0.050000000000000044`; world underside at peak approximately `{x:0.5,y:0.05}`; ground height `0.1`. Actual vertical clearance there is **−0.05 inch**, while `pose.min` is positive. This is a synthetic boundary case, not a claim that the supplied home driveway has this defect. A whole-sweep false-clear verdict was not established; the pose-level missed collision is established.

**Proposed change.** For each transformed underside segment, evaluate its endpoints and every ground vertex within its horizontal span; these cover minima of the difference of piecewise-linear functions. Handle vertical transformed segments explicitly. Separately bound or refine travel-position sampling and describe remaining approximation limits.

**Done state.** The reproduction reports the negative gap; both orientations have independent vertex/contact boundary cases; the page distinguishes checked textbook examples from general numerical accuracy.

**Verification command.** After obtaining the reviewed source, `node --test tests/driveway-geometry.test.mjs`, including a regression asserting the reproduction's minimum is approximately −0.05. Compare representative coarse sweeps with finer sweeps; do not claim that comparison alone proves all profiles.

## 2. Before announcement: invalid profile edits leave an authoritative old answer visible

**Problem.** Clearing a driveway cell leaves the prior headline, verdict table, scene and chart visible. Users can read an answer for a profile that is no longer the one on screen. Car validation already clears the headline/table; profile parsing does not.

**Evidence.** Remote `static/js/driveway-clearance.js:673` catches parsing errors at line 678 by changing only `dc-error`. On the live default sedan, clearing the first driveway distance input and dispatching `input` produced `every driveway cell needs a number.` while the headline remained `this car scrapes, whichever way it goes in.` and both verdict rows still reported underbody hits by 0.3 inch. `showError` at line 148 clears the headline/table but retains the previous analysis state. This distinction also matters for animation and sharing during invalid input.

**Proposed change.** Use a common invalid-state transition for car/profile/margin errors. Hide or explicitly mark obsolete analysis, stop animation, and prevent sharing an answer as current until valid recomputation succeeds. Preserve typed values so correction is easy.

**Done state.** Blank, duplicate-distance and nonnumeric profile inputs cannot display an unlabeled prior answer; correcting them restores both directions and controls.

**Verification command.** Run `node --test tests/driveway-geometry.test.mjs` plus a browser regression: load the live-equivalent page, clear a profile cell, assert the alert and absence of current verdicts, restore it, and assert refreshed verdicts. Geometry tests alone do not verify this UI defect.

## 3. Before announcement: phone results clip the “show me” controls

**Problem.** At phone width, the results table is wider than its container and clips the primary jump-to-collision buttons. The page itself does not horizontally scroll to reveal the missing part.

**Evidence.** Live Chromium preview at **375 × 812 CSS pixels**, default sedan: document scroll width 375; results table container width 335; `#dc-results` width **375.265625**. The first show-me button occupied x≈294–383, beyond the table's right edge at x=355. Visual inspection confirmed the button text clipped at that edge. The profile editor also measured about 392 pixels wide; its overflow needs a usable scroll treatment. At **1440 × 900**, results, scene and chart rendered legibly with document width equal to viewport width. Remote page markup: `content/posts/driveway-clearance.md:46`.

**Proposed change.** Reflow the verdict rows at narrow widths (or provide an explicit reachable horizontal scroll container); keep direction, verdict, detail and action together. Give the editor a deliberate scroll treatment without clipping controls.

**Done state.** At 320 and 375 CSS pixels and desktop width, every verdict/action is readable and reachable by touch and keyboard; the scene/chart remain usable.

**Verification command.** Browser check at 320×812, 375×812, and 1440×900: inspect each results button's bounding rectangle against its visible container, focus it with the keyboard, activate both show-me buttons, and inspect the profile editor. Existing Node geometry tests cannot prove layout.

## 4. Before announcement: “too close to call” becomes “makes it” in the headline

**Problem.** The summary encourages traversal even when the classification intentionally communicates uncertainty. This is particularly misleading because the page's Lexus example explains that a too-close result can scrape in reality.

**Evidence.** Selecting the compact hatchback live produced `this car makes it, but with less than 1.0 in to spare. go slowly.` Remote `static/js/driveway-clearance.js:222` uses this wording whenever neither direction scrapes and at least one is within the safety margin. The page's measurement guidance says anything closer than the margin is too close to call, and its real-world ES330 discussion says to interpret that result as probably scraping on this driveway.

**Proposed change.** Make the headline preserve the uncertain verdict, naming the affected directions rather than asserting success or prescribing speed. Retain the rigid-model explanation near the result.

**Done state.** Clear/clear, tight/tight, clear/tight, scrape/tight and scrape/clear summaries agree with their detailed classifications.

**Verification command.** Browser-select compact hatchback with the default 1-inch margin and assert an uncertain headline; exercise all verdict combinations with a focused UI check. Run `node --test tests/driveway-geometry.test.mjs` for geometry regression coverage.

## 5. Follow-up: invalid safety margins silently keep a different active value

**Problem.** A blank or negative margin remains displayed while computation silently retains the preceding margin. The number shown and classification threshold can disagree.

**Evidence.** Live setting `dc-margin` to `-1` and dispatching `input` left `dc-error` empty and retained the existing headline. Remote `static/js/driveway-clearance.js:621` updates state only when the value is finite and nonnegative, without an else/error path.

**Proposed change.** Validate the margin through the same invalid-state path as other measurements, and make the active threshold unambiguous.

**Done state.** Blank/negative margin gives an accessible error and no current verdict; zero and positive margins recompute correctly.

**Verification command.** Browser regression with margin values `1`, blank, `-1`, `0`, `2`; assert visible validity and the threshold used by both verdict rows.
